# Архитектура

```text
game.json
  → единожды задаёт имя продукта, Steam AppID, процесс, пути, target matchers и launchStrategy
OMORI Translator.app / OMORI Translator.exe
  → запускает helper для Gemini/LM Studio/OpenAI-compatible, журналов и ассетов на случайном порту 127.0.0.1
  → запускает Steam AppID 1150690 нативно или в бутылке CrossOver
  → Electron открывает локальный debugging port на 127.0.0.1
  → универсальный нативный контроллер подключается только к странице, совпавшей с target matchers
  → translator.bundle.js = core + languages + providers + runtime helpers/panel + generated game config + OMORI adapter + runtime
  → адаптер задаёт DOM-правила, runtime создаёт изолированную панель в Shadow DOM
  → Bulk Translate читает атомарный asset index или расшифровывает изменившиеся .HERO рядом с выбранной копией игры
  → Story/Full canvas-хуки применяют готовый кэш без сетевых запросов; Screen переводит видимый снимок только по явной кнопке
  → MutationObserver регистрирует изменённые блоки, а IntersectionObserver запускает перевод только при их появлении возле экрана
```

Перевод и показ перевода — разные стадии:

1. `Bulk Translate All Assets` получает поддерживаемый текст из отдельного постоянного asset index, выполняет массовый перевод и записывает индивидуальные пары «исходник → перевод» в IndexedDB. При первом запуске, повреждении индекса либо изменении состава, размера или `mtime_ns` `.HERO` helper заново расшифровывает файлы и атомарно заменяет индекс. Индекс привязан к каноническому каталогу выбранной копии игры; частичный результат с ошибками чтения не сохраняется.
2. Автоматические DOM- и canvas-хуки Story/Full не вызывают провайдеры перевода. Они нормализуют фактически показанную исходную строку, ищут совпадение в RAM/IndexedDB и перерисовывают элемент готовым переводом. При промахе кэша остаётся исходный английский текст.
3. `Screen Translation` не извлекает `.HERO`. После нажатия `Translate current screen` runtime собирает только видимые сейчас DOM-узлы и строки активных `Window_Base`, а адаптер одобряет эти строки для конкретных окон текущей сцены. Отключённая по умолчанию опция `Automatically translate completed dialogue` разрешает тот же fresh-request путь только для страницы `Window_Message` после её `onEndOfText`; меню она не захватывает. Runtime проверяет индивидуальные RAM/imported-pack cache keys и переводит оставшиеся строки выбранным провайдером. Свежие короткие canvas-строки объединяются защищёнными контекстными пакетами максимум по 12, после чего результат снова раскладывается по индивидуальным cache keys. `Bitmap.clear`, `createContents`, смена сцены или новый DOM-контент снимают одобрение.

Режимы перевода имеют отдельную архитектурную границу. Стабильный `Story Translation` разрешает адаптеру работать только с поверхностями диалога: репликами, именами и вариантами ответа. Экспериментальный `Full Translation` хранится отдельным `translationScope` и не расширяет dialogue matchers. Он сопоставляет `Bitmap contents → Window_Base owner`, перехватывает целую строку в `drawText`/`drawTextEx` только для недиалоговых окон и читает перевод через тот же cache-only API runtime. `Screen Translation` использует тот же безопасный перехват, но адаптер дополнительно отдаёт runtime снимок только видимых строк. Для сообщений адаптер точечно разрешает динамические `\\V`/`\\N`/`\\P`/`\\G`-токены, поэтому ключ содержит фактическое `You found 3 APPLES`, но дословно сохраняет `<WordWrap>`, команды говорящего и управления потоком. Полный `convertEscapeCharacters` выполняется только перед игровой отрисовкой перевода, а прямая перерисовка завершённой страницы предварительно вызывает YEP `setWordWrap`. Provider request разрешает runtime после явной кнопки либо после `onEndOfText`, когда пользователь отдельно включил автоматическую Screen-опцию; сам адаптер провайдер не вызывает. Внутренний флаг страницы исключает повторный запрос после перерисовки перевода. `Window_Message`, `Window_NameBox` и `Window_ChoiceList` остаются на проверенных специализированных хуках. Смена scope или Translation/Original обходит активное дерево окон и вызывает безопасный `refresh`, поэтому меню восстанавливается без перезапуска. Отдельные sprite-bitmap без `Window_Base` owner намеренно не перехватываются.

Титульный экран `Scene_OmoriTitleScreen` является сознательным исключением из canvas-подстановки: команды и подсказки остаются оригинальными, чтобы сохранить штатную типографику и избежать обрезания длинных переводов. Остальные сцены продолжают использовать локальный кэш.

Для переведённых недиалоговых `drawText`/`drawTextEx` адаптер сначала уменьшает кириллический fallback-шрифт на 8 px относительно штатного размера OMORI, затем измеряет видимую часть строки через `Bitmap.measureTextWidth`. При превышении переданной или вычисленной ширины размер дополнительно уменьшается пропорционально, с нижней границей 16 px, и восстанавливается в `finally` после одного draw-вызова. Диалоги и Original не используют эту коррекцию. Cache identity и сама строка перевода от layout-решения не зависят.

Архитектура разделена на четыре слоя:

- `src/games/<game-id>/game.json` — идентичность, язык источника, проверенные версии, ресурсы, данные сборки и запуска конкретной игры;
- `src/games/<game-id>/adapter.js` — правила игрового DOM, canvas и API отрисовки;
- `src/games/<game-id>/tests/` — обязательные проверки конкретного адаптера;
- `src/controller/main.swift` и платформенные лаунчеры — универсальное внедрение, получающее идентичность игры из манифеста.

Сборщик проверяет схему и безопасные пути манифеста, генерирует из него браузерную конфигурацию, а затем включает DOM-адаптер перед runtime. В адаптере больше нет копий названия, `id`, языка и namespace. Детальный контракт находится в `docs/ADAPTER_CONTRACT.md`.

Для локального цикла `docs/DEV_MAP.md` связывает каждую область с минимальным набором исходников и тестов. `scripts/test-runtime.sh` и `scripts/test-service.sh` дают краткие адресные проверки; полный `scripts/test-omori.sh` остаётся обязательной межслойной и релизной проверкой. Корневой `AGENTS.md` хранит только инварианты и границы модулей, поэтому handoff-промт не повторяет README, changelog и QA-отчёт.

`launchStrategy` отделяет технологию запуска от DOM-адаптера. Сейчас реализована стратегия `electron-cdp`; неизвестное значение останавливает сборку. Это оставляет явную точку расширения для другой технологии новелл без ложного запуска через Electron.


Каждый переведённый игровой блок получает нормализованный BCP 47-атрибут `lang`. Для RTL дополнительно применяются `dir="rtl"`, `direction: rtl`, `unicode-bidi: plaintext` и `text-align: start`; для CJK — правила строкового разбиения, для высоких письменностей — безопасная высота строки. Исходный шрифт игры дополняется цепочкой системных и Noto-шрифтов для выбранной письменности. Кнопкам разрешено увеличиваться и переносить длинный текст. Перед изменением все затронутые атрибуты и inline-стили сохраняются и затем восстанавливаются при `Original`, смене языка или сбросе.


Перед единым provider contract работает лексический слой `translation-core.js`. Он сканирует строку слева направо и выделяет точные токены: длинные RPG Maker-команды с `[]`/`<>`, фактические безаргументные команды полного английского корпуса (`\itemget`, `\LECLEAR`, `\OOOO`, `\spxh`, `\sxbf`, `\shaw` и speaker-коды, включая `\art`/`\ber`), односимвольные escapes включая `\"`, `<...>`, `[...]` и `VRCTXSEP<n>X`. Для всех провайдеров действует один сегментный конвейер: ни один защищённый игровой токен не отправляется модели. Несколько видимых частей сначала объединяются одной markup-free контекстной попыткой через нейтральные `VRCTXSEP<n>X`; exact parser принимает её только при сохранении всех разделителей. Повреждение разделителя или итоговой quality-проверки включает изолированный перевод тех же частей. После этого ответы сшиваются с побайтно исходным skeleton.

Сегментная сборка сохраняет исходные пробелы вокруг жёстких flow-кодов (`\!`, `\.`, `\|`, `\^`, `\{`, `\}`, `\\`), `<br>`, prefix- и terminal-команд. Пунктуация непосредственно после flow-кода и placeholder-символы также становятся локальными токенами. Слабая модель поэтому физически не может изменить или переставить служебную разметку. Финальная layout-проверка выполняется до IndexedDB и повторно при чтении RAM/fuzzy cache; придуманная моделью команда отклоняется как `markup_format_invalid`.

До обращения к провайдеру runtime удаляет из Bulk строки без переводимого текста, font coverage, Base64-содержимое ROBOHEART, подписи этажей вида `1F` и camelCase engine keys вида `DW itemBuyingPromptMessage`. ALL CAPS локально нормализуется для модели и возвращается к исходному display-case после ответа. Общая quality-проверка требует сохранения числовых и валютных литералов, отклоняет очевидную потерю предложений, аномальное разрастание/повторение и существенный перенос исходных английских слов в кириллический результат. Ошибка `translation_quality_invalid` не создаёт cache entry; исходная строка остаётся доступной для повторного прохода или другого провайдера.

Защита имеет identity `omori-markup-v3`, включённую в provider variant cache key. IndexedDB schema 5 очищает несовместимый provider-store `translations`, но сохраняет отдельный store `translationPackEntries` schema 4 со всеми импортированными packs. Контекстный Google-путь дополнительно имеет identity `google-context-v1`, поэтому прежние Google-ответы не подхватываются новым проходом. Одноразовая узкая миграция удаляет только ключи текущей игры, выбранного языка, provider `google` и прежнего fingerprint `omori-markup-v3`; другие языки, провайдеры, новый context variant и imported-pack store не совпадают с предикатом. Сохранения игры, настройки и credential vault сохраняются.

IndexedDB остаётся полным постоянным кэшем без фиксированного лимита. RAM-кэш работает как LRU и удерживает не более 50 000 последних записей. Ключ v3 включает `game-id`, провайдера и язык. Ключ v4 дополнительно содержит fingerprint варианта провайдера; для LM Studio это идентификатор модели и версия prompt, а для OpenAI-compatible AI — preset, Base URL, модель и версия prompt. Число записей и байты ведутся в компактных метаданных `localStorage`. Перед каждой мутацией устанавливается dirty-маркер; RAM и метаданные меняются только после `transaction.oncomplete`, а error/abort возвращается вызывающей операции. Маркер снимается только после сохранения новых метаданных; при аварии или несовпадении `objectStore.count()` статистика восстанавливается потоковым курсором.

Чужой cache-файл импортируется как отдельный translation pack, а не сливается с provider store. Первый потоковый проход валидирует формат, `gameId`, каждый language/provider/model scope и точное расположение защищённой OMORI-разметки; до подтверждения запись не начинается. Модалка позволяет выбрать язык и, если файл смешанный, конкретный provider/model variant. Второй проход пишет новый случайный pack ID пакетами по 250 записей; метаданные делают его активным только после полного успешного прохода. Предыдущий pack остаётся активным до этой точки, поэтому ошибка не оставляет частично установленный перевод. Lookup сначала проверяет активный pack выбранного языка, затем собственный кэш текущего провайдера. Удаление pack возвращает собственный кэш без перезаписи или потери данных.

Во время Bulk и Test Phrase runtime добавляет каждый обработанный результат в живой журнал безопасными `textContent`-узлами; кэш-попадания получают видимую отметку `cache`. Поэтому повторный проход не выглядит зависшим до первого сетевого запроса. Обычное cache-only применение игрового текста в Story или Full логирование не включает. Живой контейнер автоматически раскрывается и обычно хранит 40 последних DOM-записей. Фиксатор `Stop scroll` отключает только автоследование: runtime сохраняет первую видимую запись и её viewport-смещение, удерживает 40 новейших строк плюс окно не более 40 строк вокруг якоря и обновляет якорь только после ручного wheel/pointer/touch/keyboard-scroll. `Resume scroll` сокращает DOM обратно до 40 записей и возвращает `scrollTop` к новым строкам; перевод и сохранение истории во время паузы не останавливаются. Runtime отправляет пары локальному helper, который под блокировкой лениво строит SHA-256-набор идентичности provider/language/source/translation и дополняет `translation-history.jsonl` только отсутствующими парами. Это позволяет восстановить историю из существующего кэша без неограниченных дублей. Авторизованные loopback endpoints возвращают до 500 последних записей (UI запрашивает 200) и потоково отдают полный JSONL для сохранения. `Clear view` сохраняет этот файл; подтверждённый factory reset через `/v1/reset` удаляет его вместе с остальными данными переводчика.

После фактического старта Bulk или Test Phrase runtime добавляет host-класс `bulkBusyHost` и растягивает Shadow DOM-панель на весь viewport. CSS скрывает все корневые секции, кроме строки прогресса и контейнера настроек; внутри контейнера остаются только растянутый журнал и строка с кнопкой именно активной операции. Заголовок, сворачивание, update status, настройки сервисов, кэш-инструменты и toolbar журнала недоступны до завершения. Счётчик слов строится только по `text`-сегментам `tokenizeProtectedMarkup`, поэтому команды OMORI не считаются словами. ETA использует скользящее окно только свежих переводов текущей операции (`newlyTranslated`/`created`): cache hit уменьшает потенциальный остаток, но не входит в числитель throughput. Пересчёт сглаживается и ставится на паузу во время подготовки провайдера и cooldown; отображаемая доля при этом остаётся словарной. Успешный результат снимает оба busy-класса автоматически. Остановленный, прерванный или неполный проход переводит рабочую область в неактивное состояние без spinner, сохраняет итоговый статус и журнал, блокирует последующие фоновые `setStatus` до решения пользователя, а busy-классы снимаются только кнопкой `Back to translator`.

Экспорт версии 2 — JSON Lines: одна строка заголовка и одна строка на запись. IndexedDB читается транзакциями по 250 элементов. При наличии File System Access API поток сразу направляется в выбранный файл; fallback создаёт `Blob` из `ReadableStream`, не удерживая массив объектов и его JSON-копию в JavaScript heap. Импорт JSONL сначала потоково валидирует весь файл, затем повторно читает его и записывает пакеты по 250 элементов, поэтому повреждённый файл не импортируется частично; прежний монолитный JSON версии 1 поддерживается для обратной совместимости.

При старте текстовые контейнеры регистрируются один раз. После этого `IntersectionObserver` сообщает только о блоках, приблизившихся к viewport, а `MutationObserver` добавляет изменённые React-узлы. Автопроход работает по этому ограниченному набору и не повторяет полный `TreeWalker` на каждой прокрутке. При `document.hidden` таймер останавливается и активный запрос отменяется. Для старых Chromium без `IntersectionObserver` сохранён совместимый, но менее экономный fallback по событию прокрутки.

Публичный сценарий сборки закреплён за одной игрой (`scripts/build-omori.sh`). Общий сборщик не имеет цели по умолчанию и требует явный `VNREVIVAL_GAME=<game-id>`, поэтому пропущенная переменная не может молча выпустить приложение с чужим адаптером. OMORI manifest указывает единый исходный `assets/icon-1024.png`, пиксельно эквивалентный игровому `app.nw/icon/icon.png`: macOS получает ICNS из `assets/AppIcon.icns`, Windows-сборщик создаёт из PNG ICO с размерами 16/24/32/48/64/128/256. Сборка macOS объединяет `arm64` и `x86_64` через `lipo`. По умолчанию применяется ad-hoc подпись; при наличии Developer ID и профиля `notarytool` включаются hardened runtime, временная метка, нотариальное заверение и stapling. Windows-сборка при наличии PFX и `osslsigncode` подписывает EXE Authenticode до упаковки.

Каталог `launcher/READY_TO_SHARE/` хранит готовые ZIP-релизы и не отслеживается Git. Сборщик создаёт и проверяет пару текущей версии — macOS и Windows — но не удаляет предыдущие готовые архивы. Распакованное macOS-приложение и служебные SHA-256 находятся в `.build/` и не смешиваются с файлами для пользователей.

Общее ядро не содержит идентичность конкретной игры. OMORI получает название, пути, matchers и ресурсы из `src/games/omori/game.json`; DOM- и canvas-правила находятся только в его адаптере.

Canvas-адаптер использует только cache-only API runtime: мгновенно проверяет `queryMemoryCache`, регистрирует промах через `registerAdapterText` и, если нужен прямой асинхронный поиск, вызывает `translateAdapterText`. Ни один из этих методов не обращается к провайдеру: поиск ограничен RAM/IndexedDB, а после попадания adapter callback перерисовывает открытые окна. Опциональный `collectVisibleTexts()` также лишь возвращает точные строки активных окон; решение о свежем запросе принимает runtime только внутри обработчика явной Screen-кнопки или включённой пользователем auto-screen опции. Полный набор `.HERO` обрабатывается только явной кнопкой `Bulk Translate All Assets`, которая сразу запускает выбранный провайдер.

Разбиение длинных запросов выполняется только по границам расширенных графем: мод не разделяет суррогатные пары, комбинируемые знаки, индийские слоги, emoji ZWJ или региональные пары флагов. Используется `Intl.Segmenter` с автономным Unicode-совместимым резервным алгоритмом.

Google имеет concurrency `1`. В Bulk runtime сначала выполняет cache-only lookup для каждой строки, а fresh-остаток собирает в контекстные блоки максимум по 12 строк; одновременно проверяются лимиты `contextLimit` по JavaScript-длине и 3200 UTF-8 байтам. Начала свежих Google-запросов разделены минимум 5 секундами. Для блока `translateProtectedText` получает `contextFallback: false` и `contextualQuality: false`: служебные separator-токены и OMORI skeleton по-прежнему обязательны, но общая эвристика всего блока не запускает скрытые запросы для каждого видимого сегмента. Ответ разбирается по separator-токенам, каждая пара отдельно проходит `translationQualityMatches` и записывается под обычным индивидуальным cache key. Если parser успешен, принятые строки сразу сохраняются, а структурированная ошибка несёт только `rejectedEntries`; runtime повторяет этот остаток без повторной отправки соседей. Бинарное деление применяется, когда из ответа нельзя принять ни одной строки, а transport-ошибка запросы не размножает. Размер ещё не отправленных блоков адаптируется независимо от этого fallback: полное отклонение многострочного блока делит текущий лимит пополам до минимума 3, частичное уменьшает его на 2, четыре чистых блока увеличивают на 2 до provider maximum. Ошибка хвоста короче 3 строк не меняет лимит. Все повторные попытки и адаптивные блоки проходят через тот же пятсекундный pacer. Кириллический carryover-фильтр исключает вытянутые вокализации и компоненты повторяющихся ALL-CAPS дефисных терминов, сохраняя прежние проверки обычного непереведённого текста, чисел, валют, разметки, усечения и runaway-повторов. Частично принятый исходный блок сбрасывает systemic-failure streak; третий последовательный блок без пригодных результатов выбрасывает `google_bulk_block_failures`, останавливает проход и сохраняет уже записанный кэш. Test Phrase остаётся последовательным проходом с интервалом 1 секунда. Оба прохода используют общий rate-limit wrapper: `HTTP 429` сохраняет в `localStorage` срок cooldown и следующую ступень backoff, обновляет обратный отсчёт раз в секунду и повторяет текущий chunk внутри той же job. Поэтому `done` и `failed` во время ожидаемой паузы не растут, а повторные ограничения увеличивают паузу с 15 до 30 и 60 минут даже при перезапуске приложения; успешный свежий запрос очищает состояние. Состояние старого формата с одним deadline автоматически читается и переводится на новую схему.

Соседние текстовые узлы одного логического блока остаются одной job и одним составным cache key с локальными разделителями `VRCTXSEP…X`. Разделители не отправляются модели: каждый текстовый фрагмент переводится через общий сегментный конвейер, затем ответ собирается и разбирается обратно по исходным узлам, поэтому теги и обработчики DOM не заменяются.



При старте runtime один раз вызывает авторизованный `/v1/update/check`. Helper с 10-секундным тайм-аутом получает только фиксированный HTTPS URL `https://vnrevival.fun/downloads/omori/latest.json`, запрещает смену host при redirect, ограничивает ответ 64 KiB и валидирует `schemaVersion`, `product`, SemVer-подобную версию, `cacheCompatibility` (`keep`/`rebuild`), положительный `cacheSchema` и до пяти непустых строк `changes` длиной не более 200 символов. Runtime дополнительно ограничивает всю операцию 12 секундами, сравнивает три числовых компонента версии и выводит результат в отдельный DOM-узел. Для доступного релиза безопасными `textContent`-элементами показываются первые три изменения; пустой список заменяется встроенной заглушкой до подключения реального источника описаний. Сбой проверки не влияет на запуск и не скрывается общим статусом Bulk. Контракт манифеста:

```json
{"schemaVersion":1,"product":"omori-translator","version":"0.9.44","cacheCompatibility":"keep","cacheSchema":3,"changes":["Placeholder improvement","Placeholder bug fix"]}
```



Gemini API key поступает в локальный мост один раз при сохранении, после чего поле панели очищается. На macOS ключ хранится в Keychain, на Windows — в Credential Manager под `game-id`; JavaScript игры не получает сохранённый секрет обратно. Запрос к Gemini отправляется локальным мостом по HTTPS с ключом в заголовке, а не в URL. Для регулируемых категорий безопасности передаётся `OFF`, однако обязательные ограничения Google остаются. Ответ запрашивается по JSON-схеме, проверяется и только затем возвращается runtime.


Если автоматический поиск не находит игру, Windows показывает стандартный диалог `.exe` и сохраняет путь в `HKCU`; macOS показывает системный выбор файла и сохраняет путь в Application Support по `game-id`. Сохранённый путь проверяется при каждом старте, после его исчезновения поиск и запрос повторяются. Имя `.exe` из манифеста по-прежнему используется для автоматического поиска.

На macOS одной проверки существования `.app` недостаточно: Steam может создать на рабочем столе одноимённый ярлык, который лишь выполняет `open steam://run/<AppID>`. Лаунчер нормализует завершающий `/`, принимает native app только при наличии `Contents/Resources/app.nw` и исполняемого файла в `Contents/MacOS`, игнорирует невалидный сохранённый путь и записывает найденный канонический путь Steam обратно в настройки.

Язык, провайдер и `translationScope` (`story`/`full`/`screen`) сохраняются сразу при изменении соответствующего элемента панели. Автоприменение кэша всегда включено и не имеет отдельного элемента управления. Настройки постоянно видимы в развёрнутом состоянии, а режим исходника/перевода представлен сегментированным toggle. Положение панели сохраняется; каждый новый runtime стартует развёрнутым. Единственная кнопка заголовка переключает полную панель и один `+`. Drag использует pointer capture, глобальные pointer-события и mouse fallback для старых NW.js; в свёрнутом состоянии сам плюсик одновременно служит областью перетаскивания. Движение задаётся через `translate3d` от фактического `getBoundingClientRect()`, чтобы не зависеть от масштабирования игрового контейнера.

Долгие кнопочные операции используют общий CSS-индикатор `working`. Для `Reset all data` индикатор включается после явного подтверждения полного удаления. Runtime вызывает защищённый `/v1/reset`, очищает оба IndexedDB store, оба RAM-кэша и все ключи namespace игры в `localStorage`; helper удаляет историю/логи, служебные индексы, credentials, сохранённый лаунчером путь игры и оставшиеся файлы прежних провайдеров. Файлы игры и сохранения OMORI сохраняются. Кнопка блокируется до завершения, а ошибка выводится в общей строке статуса.

После внедрения Windows-лаунчер хранит дескриптор именно запущенного экземпляра игры, сверяет полный путь исполняемого файла и выбранную CDP-страницу. При ошибке запуска или внедрения cleanup останавливает только экземпляр, созданный этим запуском; после успешной инъекции игра остаётся жить независимо от лаунчера. CDP-ответы разбираются структурным ограниченным JSON-сканером с точным сопоставлением числового `id`.


Мод принципиально не заменяет `innerHTML`: это сохраняет теги, обработчики кликов и структуру React. Стилизованный абзац остаётся одной job, но общий защищённый конвейер переводит его текстовые фрагменты отдельно и возвращает собранный результат в существующие текстовые узлы.
