# Архитектура

```text
src/games/catalog.json
  → задаёт порядок игр в нативном стартовом выборе
единое приложение
  → пользователь выбирает игру до поиска установки и запуска процессов
  → загружает её game.json: identity, Steam/process/paths, target matchers, launchStrategy и translationStrategy
  → запускает выбранный game-configured helper для провайдеров, журналов и разрешённых capabilities на случайном порту 127.0.0.1
  → запускает Steam AppID из манифеста нативно или в бутылке CrossOver
  → Electron открывает локальный debugging port на 127.0.0.1
  → универсальный нативный контроллер подключается только к странице, совпавшей с target matchers
  → translator.bundle.js = core + languages + providers + runtime helpers/panel + generated game config + выбранный adapter + runtime
  → адаптер задаёт DOM-правила, runtime создаёт изолированную панель в Shadow DOM
asset-cache (OMORI)
  → Bulk читает атомарный asset index; Story/Full остаются cache-only; Screen переводит явный снимок
realtime-dom (прототип CoC2)
  → переводит только видимый/изменившийся DOM; asset endpoint и все bulk-операции отключены
  → MutationObserver регистрирует изменённые блоки, а IntersectionObserver запускает перевод только при их появлении возле экрана
```

Каждая сборка приложения содержит проверенный `src/games/catalog.json` и отдельную пару `games/<game-id>/game.json` + `translator.bundle.js` для каждой записи. macOS строит системный список из bundled-каталога, Windows — из сгенерированного C-заголовка с тем же порядком. Отмена выбора завершает лаунчер без запуска helper или игры. Только после выбора вычисляются Steam AppID, executable, каталог данных, CDP matchers, bundle и helper config; сохранённые пути и runtime-данные остаются game-specific.

`src/languages.txt` задаёт продуктовый каталог, а `src/languages.js` является его browser-представлением. Оба файла содержат ровно 30 канонических локалей VN Revival в том же порядке, что `SITE_LOCALE_CODES` сайта. Этот единый массив ограничивает сохранённую настройку, селектор, Bulk и импортированные pack metadata. `game.json.officialLocalizations` отдельно задаёт встроенные языки конкретной игры. Для OMORI это `en`, `ja`, `ko` и `zh`: при их выборе runtime прекращает cache/provider-применение, снимает уже применённый перевод, показывает game-specific уведомление и блокирует все элементы Shadow DOM кроме селектора языка. Test Phrase и Super Bulk исключают эти языки и обрабатывают оставшиеся 26. Старые коды `zh-CN` и `pt` нормализуются в `zh` и `pt-BR` для настройки и импортированных паков; Google-кэш этих двух локалей остаётся доступным через совместимый legacy lookup. Provider-кэш десяти удалённых кодов очищается один раз в namespace каждой игры; imported packs, история и остальные пользовательские данные сохраняются.

`translationStrategy` является исполняемым capability-контрактом, а не декоративной метаданной. `asset-cache` требует профиль и тестовую фразу и открывает OMORI asset workflow. `realtime-dom` принудительно выбирает scope `screen`, по умолчанию следит за видимым DOM и разрешает свежие запросы этого автопрохода; строки из `input`, `textarea`, `select`, `contenteditable` и game-specific приватных селекторов исключаются. В этом режиме runtime скрывает asset controls и повторно проверяет capability в самих обработчиках, а helper возвращает `asset_extraction_disabled` до поиска файлов. Поэтому CoC2-прототип не сканирует, не расшифровывает и не индексирует ассеты даже при прямом обращении к helper API.

Перевод и показ перевода — разные стадии:

1. `Bulk Translate All Assets` получает поддерживаемый текст из отдельного постоянного asset index schema 5, выполняет массовый перевод и записывает индивидуальные пары «исходник → перевод» в IndexedDB. Обычные `.HERO` дают как однострочные, так и YAML block-scalar значения `text:` с тем же folding/chomping, который видит игра. `System.HERO` дополнительно отдаёт видимые скаляры из разделов `terms` и `plugins`, включая точные варианты option-заголовков с двоеточием; `XX_BLUE.HERO` — видимые команды Options, подписи save/load и названия глав. Технические таблицы клавиш, координаты, booleans и внутренние message-ссылки исключаются. Из зашифрованных RPG Maker-баз helper читает только явный список `Actors/Armors/Classes/Enemies/Items/Skills/States/System/Weapons.KEL` и только отображаемые поля вроде `name`, `description`, системных terms и state messages. Формулы, note, параметры механики, плагины и события не индексируются. Для собираемых Equip-плагином подписей системные параметры дополнительно получают точные экранные формы `HEART:`, `JUICE:`, `ATTACK:`, `DEFENSE:`, `SPEED:`, `LUCK:` и `HIT:`. При первом запуске, повреждении индекса, изменении его схемы либо состава, размера или `mtime_ns` любого входного `.HERO`/`.KEL` helper заново расшифровывает файлы и атомарно заменяет индекс. Индекс привязан к каноническому каталогу выбранной копии игры; частичный результат с ошибками чтения не сохраняется. Контрольный индекс установленной Steam-копии содержит 217 файлов (208 `.HERO` и 9 `.KEL`) и 14 753 уникальные строки; `core.hasTranslatableText` оставляет 14 587 Bulk jobs. Точные намеренно непрозрачные/иноязычные реплики ROBOHEART, SNOW ANGEL, BUTLER MOLE и VEGGIE KID в план не входят; cache-only адаптер может заменить готовое имя говорящего, но сохраняет их payload побайтно.

Asset index schema 5 хранит рядом со строкой прозрачный контекст: тип текста, `speakerId`, исходное имя, способ определения, файл и message section. Для диалогов helper сначала использует явные `\\n<NAME>` и OMORI speaker-команды из профиля, затем выводит персонажа по устойчивой связи `faceset + faceindex`, подтверждённой несколькими явно подписанными репликами. Неоднозначная или неподтверждённая реплика получает `NARRATOR`; интерфейс и database-текст получают `SYSTEM`. Одинаковый исходник с конфликтующими персонажами также считается наррацией.

`src/omori-localization-profile.json` — проверяемый bundled-профиль локализации: стиль, открытый список speaker-кодов и глоссарий. Helper также умеет читать целевой профиль `localization-profiles/omori-<language>.json` из data directory — это точка подключения будущей синхронизации с сайтом. Полный профиль сериализуется детерминированно в стабильный system prompt, а изменяемые `source + context` идут отдельным user message. Fingerprint профиля, версия prompt и версия speaker-context входят в AI provider cache variant; обновление профиля не удаляет прежние записи, но не позволяет использовать их как переводы нового профиля. Google-путь профилем не изменяется. Обычный Story/Full gameplay по-прежнему не делает provider-запросов.

При загрузке provider-кэша OMORI-адаптер может вывести слитный псевдоним имени RPG Maker из переведённых speaker-команд: например, `HUSH PUPPY` соответствует database-форме `HUSHPUPPY`. Alias принимается только при двух или более одинаковых quality-valid переводах выбранного provider/language и отсутствии равного по частоте конфликта. Он существует только в RAM, импортированный pack по-прежнему имеет приоритет, а gameplay не делает запросов и не записывает производную пару в IndexedDB.
2. Автоматические DOM- и canvas-хуки Story/Full не вызывают провайдеры перевода. Они нормализуют фактически показанную исходную строку, ищут совпадение в RAM/IndexedDB и перерисовывают элемент готовым переводом. При промахе кэша остаётся исходный английский текст.
3. `Screen Translation` не извлекает `.HERO`. После нажатия `Translate current screen` runtime собирает только видимые сейчас DOM-узлы и строки активных `Window_Base`, а адаптер одобряет эти строки для конкретных окон текущей сцены. Отключённая по умолчанию опция `Automatically translate completed dialogue` разрешает тот же fresh-request путь только для страницы `Window_Message` после её `onEndOfText`; меню она не захватывает. Runtime проверяет индивидуальные RAM/imported-pack cache keys и переводит оставшиеся строки выбранным провайдером. Свежие короткие canvas-строки объединяются защищёнными контекстными пакетами максимум по 12, после чего результат снова раскладывается по индивидуальным cache keys. `Bitmap.clear`, `createContents`, смена сцены или новый DOM-контент снимают одобрение.

Режимы перевода имеют отдельную архитектурную границу. Стабильный `Story Translation` разрешает адаптеру работать только с поверхностями диалога: репликами, именами и вариантами ответа. Экспериментальный `Full Translation` хранится отдельным `translationScope` и не расширяет dialogue matchers. Он сопоставляет `Bitmap contents → Window_Base owner`, перехватывает целую строку в `drawText`/`drawTextEx` только для недиалоговых окон и читает перевод через тот же cache-only API runtime. `Screen Translation` использует тот же безопасный перехват, но адаптер дополнительно отдаёт runtime снимок только видимых строк. Для сообщений адаптер точечно разрешает динамические `\\V`/`\\N`/`\\P`/`\\G`-токены, поэтому ключ содержит фактическое `You found 3 APPLES`, но дословно сохраняет `<WordWrap>`, команды говорящего и управления потоком. Полный `convertEscapeCharacters` выполняется только перед игровой отрисовкой перевода, а прямая перерисовка завершённой страницы предварительно вызывает YEP `setWordWrap`. Provider request разрешает runtime после явной кнопки либо после `onEndOfText`, когда пользователь отдельно включил автоматическую Screen-опцию; сам адаптер провайдер не вызывает. Внутренний флаг страницы исключает повторный запрос после перерисовки перевода. `Window_Message`, `Window_NameBox` и `Window_ChoiceList` остаются на проверенных специализированных хуках. Смена scope или Translation/Original обходит активное дерево окон и вызывает безопасный `refresh`, поэтому меню восстанавливается без перезапуска. Отдельные sprite-bitmap без `Window_Base` owner намеренно не перехватываются.

Обход смены режима и cache-sync вызывает `refresh` только у фактически видимых открытых окон с ненулевыми `openness` и `contentsOpacity`. Закрытый `Window_NameBox` обновляется только вместе с открытым текущим `Window_Message` и непустым source: это не позволяет асинхронной синхронизации после загрузки проявить пустой dimmed-фон, тогда как активное имя продолжает получать готовый перевод.

Титульный экран `Scene_OmoriTitleScreen` является сознательным исключением из canvas-подстановки: команды и подсказки остаются оригинальными, чтобы сохранить штатную типографику и избежать обрезания длинных переводов. Остальные сцены продолжают использовать локальный кэш.

Для переведённых недиалоговых `drawText`/`drawTextEx` адаптер сначала уменьшает кириллический fallback-шрифт на 8 px относительно штатного размера OMORI, затем измеряет видимую часть строки через `Bitmap.measureTextWidth`. Для `drawTextEx` доступная ширина вычисляется по `contents.width - x`: штатный API RPG Maker не имеет аргумента ширины, а передаваемое OMORI четвёртое значение `28` не является 28 px. Вычисленный target временно закрепляется поверх внутреннего `resetFontSettings()` и восстанавливается вместе с исходным методом в `finally`. Обычная нижняя граница остаётся 16 px; точные фиксированные колонки верхнего `Window_MenuCommand` и `Window_OmoMenuItemList` используют соответственно 12 и 8 px, потому что измеренные cache-hit строки иначе физически шире доступных 92/164 px. Переведённые описания `Window_OmoMenuHelp` получают штатный YEP `<WordWrap>`; при `IconIndex` адаптер вычитает 106 px под рисунок, буквальные переводы строк преобразует в `<br>`, а соседнюю пару `<br>\n` считает одним переносом. Диалоги и Original не используют эту коррекцию. Cache identity и сама строка перевода от layout-решения не зависят.

Архитектура разделена на четыре слоя:

- `src/games/<game-id>/game.json` — идентичность, язык источника, официальные локализации, проверенные версии, ресурсы, данные сборки и запуска конкретной игры;
- `src/games/<game-id>/adapter.js` — правила игрового DOM, canvas и API отрисовки;
- `src/games/<game-id>/tests/` — обязательные проверки конкретного адаптера;
- `src/controller/main.swift` и платформенные лаунчеры — универсальное внедрение, получающее идентичность игры из манифеста.

Сборщик проверяет схему и безопасные пути манифеста, генерирует из него браузерную конфигурацию, а затем включает DOM-адаптер перед runtime. В адаптере больше нет копий названия, `id`, языка и namespace. Детальный контракт находится в `docs/ADAPTER_CONTRACT.md`.

Для локального цикла `docs/DEV_MAP.md` связывает каждую область с минимальным набором исходников и тестов. `scripts/test-runtime.sh` и `scripts/test-service.sh` дают краткие адресные проверки; полный `scripts/test-omori.sh` остаётся обязательной межслойной и релизной проверкой. Корневой `AGENTS.md` хранит только инварианты и границы модулей, поэтому handoff-промт не повторяет README, changelog и QA-отчёт.

`launchStrategy` отделяет технологию запуска от DOM-адаптера. Сейчас реализована стратегия `electron-cdp`; неизвестное значение останавливает сборку. Это оставляет явную точку расширения для другой технологии новелл без ложного запуска через Electron.


Каждый переведённый игровой блок получает нормализованный BCP 47-атрибут `lang`. Для RTL дополнительно применяются `dir="rtl"`, `direction: rtl`, `unicode-bidi: plaintext` и `text-align: start`; для CJK — правила строкового разбиения, для высоких письменностей — безопасная высота строки. Исходный шрифт игры дополняется цепочкой системных и Noto-шрифтов для выбранной письменности. Кнопкам разрешено увеличиваться и переносить длинный текст. Перед изменением все затронутые атрибуты и inline-стили сохраняются и затем восстанавливаются при `Original`, смене языка или сбросе.


Перед единым provider contract работает лексический слой `translation-core.js`. Он сканирует строку слева направо и выделяет точные токены: длинные RPG Maker-команды с `[]`/`<>`, фактические безаргументные команды полного английского корпуса (`\itemget`, `\LECLEAR`, `\OOOO`, `\spxh`, `\sxbf`, `\shaw` и speaker-коды, включая `\art`/`\ber`), односимвольные escapes включая `\"`, `<...>`, `[...]` и `VRCTXSEP<n>X`. Для всех провайдеров действует один сегментный конвейер: ни один защищённый игровой токен не отправляется модели. Несколько видимых частей сначала объединяются одной markup-free контекстной попыткой через нейтральные `VRCTXSEP<n>X`; exact parser принимает её только при сохранении всех разделителей. Повреждение разделителя или итоговой quality-проверки включает изолированный перевод тех же частей. После этого ответы сшиваются с побайтно исходным skeleton.

Сегментная сборка сохраняет исходные пробелы вокруг жёстких flow-кодов (`\!`, `\.`, `\|`, `\^`, `\{`, `\}`, `\\`), `<br>`, prefix- и terminal-команд. Placeholder-символы остаются локальными токенами, а соседняя пунктуация входит в видимый сегмент: так добавленный провайдером знак не дублирует отдельный punctuation-token в skeleton. Слабая модель поэтому физически не может изменить или переставить служебную разметку. Финальная layout-проверка выполняется до IndexedDB и повторно при чтении RAM/fuzzy cache; придуманная моделью команда отклоняется как `markup_format_invalid`. Единственное разрешённое различие fuzzy-layout — runtime-добавка начального `<WordWrap>`: lookup переносит точный wrapper исходника на найденный перевод, но повторно требует совпадения speaker-кода и всей остальной защищённой структуры.

До обращения к провайдеру runtime удаляет из Bulk строки без переводимого текста, font coverage, Base64-содержимое ROBOHEART, подписи этажей вида `1F` и camelCase engine keys вида `DW itemBuyingPromptMessage`. К этому же непрозрачному классу относятся три speaker-wrapped Base64-реплики ROBOHEART и намеренно латинская цитата SNOW ANGEL: при отрисовке Full адаптер cache-only переводит только имя говорящего, а payload сохраняет точно, не создавая provider-запроса на cache miss. ALL CAPS локально нормализуется для модели и возвращается к исходному display-case после ответа. Общая quality-проверка требует сохранения числовых и валютных литералов, отклоняет очевидную потерю предложений, аномальное разрастание/повторение и существенный перенос исходных английских слов в кириллический результат. Для кириллической цели полностью неизменённый латинский ответ с словом длиной от четырёх букв также считается `english_carryover`; короткие аббревиатуры вроде `DVD` остаются допустимыми. Старые provider cache entries, нарушающие актуальный quality gate, не удаляются и не применяются в Full: следующий явно запущенный Screen/Bulk может перезаписать их, тогда как импортированный pack сохраняет приоритет. Ошибка `translation_quality_invalid` не создаёт cache entry; исходная строка остаётся доступной для повторного прохода или другого провайдера.

Canvas-fit использует фактическую ширину bitmap и временно уменьшает только переводимую строку, после чего восстанавливает исходный размер шрифта. `Window_OmoriFileInformation` имеет дополнительную геометрию: оригинальный Save & Load-плагин рисует `FILE n:`, `LEVEL:`, `TOTAL PLAYTIME:` и `LOCATION:` в прямоугольниках, которые пересекаются с главой и значениями. Адаптер ограничивает эти четыре уже закэшированные подписи реальными ширинами их левых колонок и допускает минимум 10 px только в этом окне; соседние глава, уровень, время и местоположение остаются в штатных координатах.

Защита имеет identity `omori-markup-v3`, включённую в provider variant cache key. IndexedDB schema 5 очищает несовместимый provider-store `translations`, но сохраняет отдельный store `translationPackEntries` schema 4 со всеми импортированными packs. Контекстный Google-путь дополнительно имеет identity `google-context-v1`, поэтому прежние Google-ответы не подхватываются новым проходом. Одноразовая узкая миграция удаляет только ключи текущей игры, выбранного языка, provider `google` и прежнего fingerprint `omori-markup-v3`; другие языки, провайдеры, новый context variant и imported-pack store не совпадают с предикатом. После перехода общего каталога на 30 локалей ещё одна одноразовая миграция удаляет из provider-store записи выведенных кодов `bn`, `ur`, `ta`, `te`, `my`, `mr`, `ml`, `kn`, `uz`, `am`. Совместимые прежние коды `zh-CN` и `pt` сохраняются для канонических `zh` и `pt-BR`; imported-pack store, история, сохранения игры, настройки и credential vault не затрагиваются.

IndexedDB остаётся полным постоянным кэшем без фиксированного лимита. RAM-кэш работает как LRU и удерживает не более 50 000 последних записей. Ключ v3 включает `game-id`, провайдера и язык. Ключ v4 дополнительно содержит fingerprint варианта провайдера; для LM Studio это идентификатор модели и версия prompt, а для OpenAI-compatible AI — preset, Base URL, модель и версия prompt. Число записей и байты ведутся в компактных метаданных `localStorage`. Перед каждой мутацией устанавливается dirty-маркер; RAM и метаданные меняются только после `transaction.oncomplete`, а error/abort возвращается вызывающей операции. Маркер снимается только после сохранения новых метаданных; при аварии или несовпадении `objectStore.count()` статистика восстанавливается потоковым курсором.

Чужой cache-файл импортируется как отдельный translation pack, а не сливается с provider store. Первый потоковый проход валидирует формат, `gameId`, каждый language/provider/model scope и точное расположение защищённой OMORI-разметки; до подтверждения запись не начинается. Модалка позволяет выбрать язык и, если файл смешанный, конкретный provider/model variant. Второй проход пишет новый случайный pack ID пакетами по 250 записей; метаданные делают его активным только после полного успешного прохода. Предыдущий pack остаётся активным до этой точки, поэтому ошибка не оставляет частично установленный перевод. Lookup сначала проверяет активный pack выбранного языка, затем собственный кэш текущего провайдера. Удаление pack возвращает собственный кэш без перезаписи или потери данных.

Во время Bulk и Test Phrase runtime добавляет каждый обработанный результат в живой журнал безопасными `textContent`-узлами; кэш-попадания получают видимую отметку `cache`. Поэтому повторный проход не выглядит зависшим до первого сетевого запроса. Обычное cache-only применение игрового текста в Story или Full логирование не включает. Живой контейнер автоматически раскрывается и обычно хранит 40 последних DOM-записей. Фиксатор `Stop scroll` отключает только автоследование: runtime сохраняет первую видимую запись и её viewport-смещение, удерживает 40 новейших строк плюс окно не более 40 строк вокруг якоря и обновляет якорь только после ручного wheel/pointer/touch/keyboard-scroll. `Resume scroll` сокращает DOM обратно до 40 записей и возвращает `scrollTop` к новым строкам; перевод и сохранение истории во время паузы не останавливаются. Runtime отправляет пары локальному helper, который под блокировкой лениво строит SHA-256-набор идентичности provider/language/source/translation и дополняет `translation-history.jsonl` только отсутствующими парами. Это позволяет восстановить историю из существующего кэша без неограниченных дублей. Авторизованные loopback endpoints возвращают до 500 последних записей (UI запрашивает 200) и потоково отдают полный JSONL для сохранения. `Clear view` сохраняет этот файл; подтверждённый factory reset через `/v1/reset` удаляет его вместе с остальными данными переводчика.

После фактического старта Bulk или Test Phrase runtime добавляет host-класс `bulkBusyHost` и растягивает Shadow DOM-панель на весь viewport. CSS скрывает все корневые секции, кроме строки прогресса и контейнера настроек; внутри контейнера остаются только растянутый журнал и строка с кнопкой именно активной операции. Заголовок, сворачивание, update status, настройки сервисов, кэш-инструменты и toolbar журнала недоступны до завершения. Счётчик слов строится только по `text`-сегментам `tokenizeProtectedMarkup`, поэтому команды OMORI не считаются словами. ETA использует скользящее окно только свежих переводов текущей операции (`newlyTranslated`/`created`): cache hit уменьшает потенциальный остаток, но не входит в числитель throughput. Пересчёт сглаживается и ставится на паузу во время подготовки провайдера и cooldown; отображаемая доля при этом остаётся словарной. Любой терминальный результат оставляет рабочую область открытой без spinner, сохраняет итоговый статус и журнал и блокирует последующие фоновые `setStatus` до решения пользователя. При успехе нижняя кнопка получает зелёное состояние `Finish`; остановленный, прерванный или неполный проход получает `Back to translator`. Только нажатие этой терминальной кнопки снимает busy-классы и возвращает меню.

Экспорт версии 2 — JSON Lines: одна строка заголовка и одна строка на запись. IndexedDB читается транзакциями по 250 элементов. При наличии File System Access API поток сразу направляется в выбранный файл; fallback создаёт `Blob` из `ReadableStream`, не удерживая массив объектов и его JSON-копию в JavaScript heap. Импорт JSONL сначала потоково валидирует весь файл, затем повторно читает его и записывает пакеты по 250 элементов, поэтому повреждённый файл не импортируется частично; прежний монолитный JSON версии 1 поддерживается для обратной совместимости.

При старте текстовые контейнеры регистрируются один раз. После этого `IntersectionObserver` сообщает только о блоках, приблизившихся к viewport, а `MutationObserver` добавляет изменённые React-узлы. Автопроход работает по этому ограниченному набору и не повторяет полный `TreeWalker` на каждой прокрутке. При `document.hidden` таймер останавливается и активный запрос отменяется. Для старых Chromium без `IntersectionObserver` сохранён совместимый, но менее экономный fallback по событию прокрутки.

`scripts/build-game-bundle.sh` собирает отдельный проверяемый browser bundle по явному `VNREVIVAL_GAME=<game-id>` и доступен для прототипов. `scripts/prepare-game-resources.sh` проходит по общему каталогу и подготавливает manifest + bundle каждой игры для единого стартового выбора. Публичный релизный сценарий и оболочка приложения пока сохраняют identity OMORI (`scripts/build-omori.sh`), но могут включать явно зарегистрированный CoC2-прототип как подписанный пользователю экспериментальный вариант; отдельная release-сборка прототипа по-прежнему запрещена проверкой `releaseStatus`. OMORI manifest указывает единый исходный `assets/icon-1024.png`, пиксельно эквивалентный игровому `app.nw/icon/icon.png`: macOS получает ICNS из `assets/AppIcon.icns`, Windows-сборщик создаёт из PNG ICO с размерами 16/24/32/48/64/128/256. Сборка macOS объединяет `arm64` и `x86_64` через `lipo`. По умолчанию применяется ad-hoc подпись; при наличии Developer ID и профиля `notarytool` включаются hardened runtime, временная метка, нотариальное заверение и stapling. Windows-сборка при наличии PFX и `osslsigncode` подписывает EXE Authenticode до упаковки.

Каталог `launcher/READY_TO_SHARE/` хранит ZIP-релизы и не отслеживается Git. Сборщик создаёт и проверяет пару текущей версии — macOS и Windows — но не удаляет предыдущие архивы и не доказывает их актуальность одним совпадением номера версии. В частности, существующие ZIP `0.9.44` датированы раньше текущего runtime/helper, всё ещё содержат прежний `argos_service.py` и не соответствуют обновлённой корневой `.app`; перед распространением их требуется отдельно пересобрать и проверить. Распакованное macOS-приложение и служебные SHA-256 находятся в `.build/` и не смешиваются с файлами для пользователей.

Общий orchestration runtime не содержит identity конкретной игры. Название, пути, matchers, update product/URL, namespaces, стратегия и необязательный профиль поступают из `src/games/<game-id>/game.json`; DOM- и canvas-правила находятся только в выбранном адаптере. `translation-core.js` сохраняет RPG Maker/OMORI markup-совместимость как допустимый superset для обычного DOM-текста, но не выбирает игру и не открывает её файлы.

Canvas-адаптер использует только cache-only API runtime: мгновенно проверяет `queryMemoryCache`, регистрирует промах через `registerAdapterText` и, если нужен прямой асинхронный поиск, вызывает `translateAdapterText`. Ни один из этих методов не обращается к провайдеру: поиск ограничен RAM/IndexedDB, а после попадания adapter callback перерисовывает открытые окна. Опциональный `collectVisibleTexts()` также лишь возвращает точные строки активных окон; решение о свежем запросе принимает runtime только внутри обработчика явной Screen-кнопки или включённой пользователем auto-screen опции. Полный набор `.HERO` обрабатывается только явной кнопкой `Bulk Translate All Assets`, которая сразу запускает выбранный провайдер.

Разбиение длинных запросов выполняется только по границам расширенных графем: мод не разделяет суррогатные пары, комбинируемые знаки, индийские слоги, emoji ZWJ или региональные пары флагов. Используется `Intl.Segmenter` с автономным Unicode-совместимым резервным алгоритмом.

Google имеет concurrency `1`. Перед Bulk runtime использует полный набор ключей уже загруженного provider/language scope, поэтому известный cache miss не создаёт отдельную IndexedDB-транзакцию. Fresh-остаток собирается в контекстные блоки максимум по 12 строк, 16 переводимым сегментам и 3200 UTF-8 байтам. Сегменты считаются после `tokenizeProtectedMarkup`, поэтому насыщенные `\c`/`\!`/`<br>` строки не превращают один запрос в десятки маркеров. Единый start-time pacer начинает с базовых `1200 ms` и добавляет к каждому интервалу независимые случайные `0–600 ms`; он применяется и к каждому фактическому retry внутри `requestChunk`/`requestChunks`. Повышение базовой задержки к `5000 ms` происходит только после полного терминального provider/network-failure блока; `translation_quality_invalid`, `markup_format_invalid`, `google_context_format_invalid` и `google_batch_format_invalid` являются локальными ошибками контента, поэтому задержку и systemic streak не увеличивают. Четыре чистых блока уменьшают повышенный интервал на секунду. Многострочный `translateProtectedText` получает `contextFallback: false` и `contextualQuality: false`, после чего каждая разобранная пара отдельно проходит `translationQualityMatches`. Принятые строки одного ответа фиксируются общей IndexedDB-транзакцией, а activity/history отправляются helper одним пакетом. Терминальный singleton и единственный quality-retry сразу используют изолированные видимые сегменты. Для Google они передаются отдельными `q` одного `/translate_a/t`-запроса; ответ принимается только как массив строк точной длины. Пустой элемент разрешён: для отдельного английского артикля это корректный русский перевод, а сборка не оставляет лишний пробел между соседними командами. Реально неправильная форма массива без повторных batch-retry откатывается к paced `/single` для сегментов. Суммы, время `10AM`, величины вроде `150mg`, числа с группировкой, одиночные цифры, длинные числа и ordinal вроде `5TH` остаются в локальном skeleton; соседняя пунктуация переводится вместе с видимым сегментом и не дублируется при сборке. Обычные многозначные числа вроде `20`/`25` передаются как один видимый фрагмент, а не как provider-текст и защищённая последняя цифра, после чего exact quality-проверка по-прежнему требует те же числовые значения; ordinal-дробь `8/8ths` сравнивается с локализованным `8/8` по двум значениям. Лит-спеллинг корпуса `2geter` нормализуется для провайдера в `together`, а quality gate считает числами только самостоятельные числовые литералы. Повторённые и неокрашенные ALL CAPS game names, quoted title-case, CamelCase и многословные Title Case-названия, а также подписи клавиш считаются сохраняемыми терминами, но обычный существенный английский carryover по-прежнему отклоняется. Для последнего `english_carryover`-отказа многочастной строки Google получает одну дополнительную контекстную попытку с разделителем `/`: exact split позволяет исправить двусмысленное слово вроде `COOKIES`, не отдавая провайдеру разметку. Бинарное деление применяется только к многострочным блокам с separator/markup-ошибкой, после чего окончательные отказы получают локальный `failed`. Test Phrase и Screen используют тот же pacer без задержки после последнего chunk, поэтому все Google-пути разделяют свежие старты минимум на 1,2 секунды без двойного ожидания. `HTTP 429` сохраняет cooldown 15/30/60 минут и повторяет текущую job. Каждый фактический запрос записывает без исходного текста stage, block size, batch items, payload bytes, latency и outcome в `translation-performance.jsonl`; итог Bulk дополнительно показывает requests и accepted/request. Источник, отклонённый кандидат, код и конкретный quality/detail каждого окончательного отказа сохраняются отдельно в локальном `translation-failures.jsonl`.

Соседние текстовые узлы одного логического блока остаются одной job и одним составным cache key с локальными разделителями `VRCTXSEP…X`. Разделители не отправляются модели: каждый текстовый фрагмент переводится через общий сегментный конвейер, затем ответ собирается и разбирается обратно по исходным узлам, поэтому теги и обработчики DOM не заменяются.

OpenAI-compatible helper извлекает только фактически возвращённый объект `usage` из каждого успешного JSON-ответа Chat Completions. Целочисленные input/prompt, output/completion, total, cached и reasoning token counts сохраняются без пересчёта; `cost` сохраняется исходным десятичным значением только когда его вернул provider. Для OpenRouter единицей являются `credits`, переданные сервисом; стоимость других endpoints без собственной currency помечается как `provider units`. Ответ без `usage` увеличивает только число ответов и явно остаётся `tokens/cost not reported`. Запись в `openai-compatible-usage.jsonl` выполняется до разбора перевода и quality/markup-проверок, поэтому оплаченный, но отклонённый ответ не теряется. Журнал не содержит исходного либо переведённого текста, агрегируется раздельно по preset и Base URL, показывается в OpenAI-compatible box и удаляется только подтверждённым `Reset all data`. Если журнал нельзя открыть до запроса, внешний вызов не начинается; ошибка записи после ответа не повторяет платный запрос.

Chat Completions запрашивается с JSON Schema, но helper принимает также fenced JSON и plain text, если совместимый endpoint проигнорировал schema; синтаксически повреждённый JSON не маскируется под перевод. Минимальный completion budget удалённого OpenAI-compatible запроса равен 2048 токенам, поскольку GLM-5.3-Flash при прежнем лимите 256 могла потратить весь ответ на reasoning и вернуть пустой `content`. Повторный reasoning-only, пустой или неподдерживаемый ответ считается фатальной ошибкой текущей Bulk/Test Phrase, чтобы одна конфигурационная несовместимость не создавала платный запрос для каждой asset job.



При старте runtime один раз вызывает авторизованный `/v1/update/check`. Helper с 10-секундным тайм-аутом получает только game-specific HTTPS URL вида `https://vnrevival.fun/downloads/<game-id>/latest.json` из проверенного bundled-манифеста, запрещает смену host при redirect, ограничивает ответ 64 KiB и валидирует `schemaVersion`, ожидаемый `product`, SemVer-подобную версию, `cacheCompatibility` (`keep`/`rebuild`), положительный `cacheSchema` и до пяти непустых строк `changes` длиной не более 200 символов. Runtime дополнительно ограничивает всю операцию 12 секундами, сравнивает три числовых компонента версии и выводит результат в отдельный DOM-узел. Для доступного релиза безопасными `textContent`-элементами показываются первые три изменения; пустой список заменяется встроенной заглушкой до подключения реального источника описаний. Сбой проверки не влияет на запуск и не скрывается общим статусом Bulk. Для OMORI контракт манифеста выглядит так:

```json
{"schemaVersion":1,"product":"omori-translator","version":"0.9.44","cacheCompatibility":"keep","cacheSchema":3,"changes":["Placeholder improvement","Placeholder bug fix"]}
```



Gemini API key поступает в локальный мост один раз при сохранении, после чего поле панели очищается. На macOS ключ хранится в Keychain, на Windows — в Credential Manager под `game-id`; JavaScript игры не получает сохранённый секрет обратно. Запрос к Gemini отправляется локальным мостом по HTTPS с ключом в заголовке, а не в URL. Для регулируемых категорий безопасности передаётся `OFF`, однако обязательные ограничения Google остаются. Ответ запрашивается по JSON-схеме, проверяется и только затем возвращается runtime.


Если автоматический поиск не находит игру, Windows показывает стандартный диалог `.exe` и сохраняет путь в `HKCU`; macOS показывает системный выбор файла и сохраняет путь в Application Support по `game-id`. Сохранённый путь проверяется при каждом старте, после его исчезновения поиск и запрос повторяются. Имя `.exe` из манифеста по-прежнему используется для автоматического поиска.

На macOS одной проверки существования `.app` недостаточно: Steam может создать на рабочем столе одноимённый ярлык, который лишь выполняет `open steam://run/<AppID>`. Лаунчер нормализует завершающий `/`, принимает native app только при наличии `Contents/Resources/app.nw` и исполняемого файла в `Contents/MacOS`, игнорирует невалидный сохранённый путь и записывает найденный канонический путь Steam обратно в настройки.

Язык, провайдер и `translationScope` (`story`/`full`/`screen`) сохраняются сразу при изменении соответствующего элемента панели. Автоприменение кэша всегда включено и не имеет отдельного элемента управления. Настройки постоянно видимы в развёрнутом состоянии, а режим исходника/перевода представлен сегментированным toggle. Положение панели сохраняется; каждый новый runtime стартует развёрнутым. Единственная кнопка заголовка переключает полную панель и один `+`. Drag использует pointer capture, глобальные pointer-события и mouse fallback для старых NW.js; в свёрнутом состоянии сам плюсик одновременно служит областью перетаскивания. Движение задаётся через `translate3d` от фактического `getBoundingClientRect()`, чтобы не зависеть от масштабирования игрового контейнера.

Долгие кнопочные операции используют общий CSS-индикатор `working`. Для `Reset all data` индикатор включается после явного подтверждения полного удаления. Runtime вызывает защищённый `/v1/reset`, очищает оба IndexedDB store, оба RAM-кэша и все ключи namespace игры в `localStorage`; helper удаляет историю/логи, служебные индексы, credentials, сохранённый лаунчером путь игры и оставшиеся файлы прежних провайдеров. Файлы игры и сохранения OMORI сохраняются. Кнопка блокируется до завершения, а ошибка выводится в общей строке статуса.

После внедрения Windows-лаунчер хранит дескриптор именно запущенного экземпляра игры, сверяет полный путь исполняемого файла и выбранную CDP-страницу. При ошибке запуска или внедрения cleanup останавливает только экземпляр, созданный этим запуском; после успешной инъекции игра остаётся жить независимо от лаунчера. CDP-ответы разбираются структурным ограниченным JSON-сканером с точным сопоставлением числового `id`.


Мод принципиально не заменяет `innerHTML`: это сохраняет теги, обработчики кликов и структуру React. Стилизованный абзац остаётся одной job, но общий защищённый конвейер переводит его текстовые фрагменты отдельно и возвращает собранный результат в существующие текстовые узлы.
